## 2026-11-22 / C · 세대 이력과 반복 상태 감지 1차

### 1. 기존 문제

- `BoardModel`은 한 세대 전후의 보드 상태를 `Snapshot`으로 만들 수 있지만, 여러 세대를 순서대로 보관하거나 이전 상태로 돌아가는 기능은 없었다.
- 같은 보드 배치가 다시 나타났는지 알려면 현재 보드와 과거 보드를 실제 칸별로 비교해야 한다. 세포 수만 비교하면 글라이더처럼 모양은 같지만 위치가 달라진 경우를 반복으로 잘못 판단할 수 있다.
- 파일 저장·불러오기는 디스크에 남기는 사용자 기능이다. 실행 중 Undo와 반복 감지를 위해서는 파일을 만들지 않고 메모리에서 빠르게 상태를 관리할 별도 구조가 필요하다.

### 2. 변경 내용

이번 단계에서는 A의 `BoardModel.Snapshot`, `snapshot()`, `restore()`, `addStepListener()`를 재사용해 새 `history` 패키지를 추가했다.

- `GenerationHistory` — 현재 상태를 포함한 최근 N개의 스냅샷을 보관한다. `BoardModel.StepListener`를 구현해 세대 완료 알림을 받으면 자동으로 기록한다.
- `GenerationHistory.undo(model)` — 한 단계 이전 스냅샷을 골라 보드와 세대 번호를 함께 복원한다. Undo 뒤 새 세대가 진행되면 기존의 미래 이력을 버리고 새 흐름을 기록한다.
- `GenerationHistory.reset(snapshot)` — Clear, Load, 규칙 변경처럼 새로운 시작점이 되는 조작 뒤 이력을 초기화한다.
- `PeriodDetector` — 저장된 범위 안에서 현재와 살아 있는 칸의 위치가 정확히 같은 과거 스냅샷을 찾는다. 세대 번호는 비교하지 않고, 위치가 같은 경우에만 주기를 계산한다.
- `PeriodDetectionResult` — 반복 시작 세대, 현재 세대, 주기를 전달한다.

### 3. 설계 결정

- A의 `Snapshot`을 다시 만들지 않고 재사용했다. 한 시점의 보드 자료는 `Snapshot`, 여러 시점의 순서와 Undo 정책은 `GenerationHistory`가 맡도록 책임을 나눴다.
- 최대 보관 개수는 현재 상태를 포함한다. 예를 들어 최대 6개면 현재 상태와 그 이전 5개를 보관한다. 제한된 이력 안에서만 반복을 판단하므로 오래된 상태가 삭제된 뒤의 반복은 추정하지 않는다.
- 반복은 세포 수가 아니라 전체 칸의 위치를 비교한다. 같은 모양이 이동한 글라이더는 같은 배치가 아니므로 반복으로 처리하지 않는다.
- `GenerationHistory`는 화면이나 파일을 직접 다루지 않는다. D의 Undo 명령과 F의 상태 패널은 이 객체를 호출하거나 결과를 읽는 방식으로 연결한다.
