## 2026-11-22 / D · Clock에서 메뉴 분리 + 편집 모드와 실행 조작 개선

### 1. 기존 문제

- 게임이 실행 중일 때 칸을 하나 찍으면 이웃이 0개라 다음 틱에 바로 죽는다. 클릭이 무시된 것처럼 보여서 처음 쓰는 사람은 버그로 착각한다. 실행 중인지 확인하지 않고 클릭을 바로 보드에 넘기기 때문이다.
- `Clock`이 타이머 역할과 Go 메뉴 생성을 함께 맡았다. 메뉴 6개가 리스너 하나를 공유하고 메뉴 이름의 첫 글자로 동작을 골랐다 (`'T'` 한 세대, `'A'` 500ms, `'S'` 150ms, `'M'` 70ms, `'F'` 30ms, 그 외 정지). `S`로 시작하는 메뉴를 새로 넣으면 Slow로 처리된다.
- "실행 중"을 나타내는 값이 없다. `TimerTask`가 null인지가 유일한 단서라 다른 코드가 지금 상태를 물어볼 수 없고 화면에 표시할 수도 없다. 상태가 바뀌어도 아무에게도 알리지 않는다.
- 불러오기·저장 전에 `Clock.instance().stop()`으로 정지만 하고, 원래 실행 중이었는지는 기억하지 않는다.

### 2. 변경 내용

입력(마우스 클릭, Go 메뉴, 단축키)은 `GameController`가 받아 현재 상태 객체에 넘긴다. 상태 객체가 타이머를 켜고 끌지, 칸을 바꿀지, 다음 상태가 무엇인지 정한다. `Clock`은 타이머만 남았다.

| 입력 | 편집 | 실행 | 일시정지 |
| --- | --- | --- | --- |
| 칸 클릭 | 토글 | 일시정지로 바꾼 뒤 토글 | 토글 |
| 실행(속도) | 실행으로 | 속도만 변경 | 실행으로 |
| 정지 (Halt) | 무시 | 일시정지로 | 무시 |
| 한 세대 진행 (Tick) | 진행 | 무시 | 진행 |
| 실행/정지 전환 (Space) | 기본 속도(Medium)로 실행 | 일시정지로 | 직전 속도로 실행 |

#### 새 패키지 `com.holub.life.control`

- **State** — `GameState` 인터페이스와 `EditingState`, `RunningState`, `PausedState`. 편집 상태는 보관하는 값이 없어 인스턴스 하나를 공유하고, 실행·일시정지 상태는 속도를 갖는다.
- **Context** — `GameController`. 현재 상태를 보관하고 입력을 상태에 넘긴다. 상태가 바뀌면 `StateListener`에게 알린다. 파일을 불러온 뒤에는 `boardReplaced()`로 편집 상태로 돌아간다.
- **타이머 의존성** — `Ticker` 인터페이스. 컨트롤러는 `Clock.instance()`를 직접 부르지 않고 생성자로 받은 `Ticker`만 쓴다. `Clock`이 이를 구현한다.
- **Command** — `Command` 인터페이스와 `RunCommand`, `PauseCommand`, `StepCommand`, `TogglePlayCommand`. 메뉴와 단축키가 같은 객체를 쓴다.
- **메뉴와 단축키** — `GoMenu`(원본과 같은 이름·순서 + `Run/Pause (Space)`), `KeyBindings`(스페이스: 실행/정지, 오른쪽 화살표: 한 세대).
- **속도** — `Speed` enum. 원본의 500/150/70/30ms를 이름 있는 상수로 옮겼다.

#### 기존 파일

| 파일 | 변경 |
| --- | --- |
| `Clock.java` | `createMenus()`와 생성자의 호출을 삭제. 메뉴용 import 정리. `implements Ticker` 추가. `startTicking()`, `stop()`, `tick()`, `menuIsActive()`는 그대로 |
| `Universe.java` | 컨트롤러 필드와 `setController()` 추가. 클릭은 `controller.cellClicked()`로, 불러오기·저장 전 정지는 `controller.pause()`로. 불러오기에 성공하면 `controller.boardReplaced()` |
| `Life.java` | 컨트롤러 생성 → `Universe`에 연결 → `GoMenu` 등록 → 단축키 등록. 현재 상태를 제목 표시줄에 표시 |

### 3. 설계 결정

- **State 패턴 vs boolean 플래그 / enum + switch** — 플래그는 상태가 둘일 때 가장 간단하지만, 상태 3개 × 입력 5개라 같은 조건문이 클릭·메뉴·단축키 처리에 흩어진다. enum + switch는 한 곳에 모이지만 상태가 늘면 모든 switch를 고쳐야 한다. 상태별 동작을 각 클래스에 모으면 위 표가 코드 구조와 그대로 맞는다. 강의자료 `10 State.pdf` 참고.
- **상태를 3개로 둘지 2개로 둘지** — 편집과 일시정지는 입력에 대한 반응이 거의 같다. 다른 점은 이어서 실행할 속도를 기억하는지(Space)와 화면 표시뿐이다. 둘을 "정지" 하나로 합치고 직전 속도를 필드로 두는 안도 가능했다. 파일을 불러온 직후처럼 "새로 시작하는 판"과 "보던 중 멈춘 판"을 사용자에게 구분해 보여주기 위해 3개로 뒀다. 상태가 적은 경우 패턴이 과할 수 있다는 점은 남은 논의 거리다.
- **Command를 따로 둔 이유** — 메뉴에 `ActionListener`를 바로 다는 것으로도 첫 글자 분기는 없앨 수 있다. 하지만 메뉴, 단축키, (앞으로) 툴바 버튼이 같은 동작을 공유하려면 Swing 이벤트와 무관한 동작 객체가 필요했다. 실행 조작은 되돌릴 필요가 없어 `execute()`만 두었다. 편집 되돌리기(Undo)용 Command와는 목적이 다르다. 강의자료 `4 Command.pdf` 참고.
- **Clock 싱글턴을 직접 부르지 않기** — 컨트롤러가 `Clock.instance()`를 부르면 테스트에서 실제 타이머 스레드가 돌아 결과가 시간에 따라 달라진다. `Ticker` 인터페이스를 두고 생성자로 받게 해서 테스트에서는 호출만 기록하는 가짜 타이머를 쓴다 (DIP). `Clock` 싱글턴 자체를 없애는 일은 A의 범위와 겹쳐서 하지 않았다.
- **실행 중 Tick을 무시** — 원본은 자동 진행 중에도 Tick을 누르면 틱을 하나 더 끼워 넣었다. 자동 진행 중 단일 진행은 의미가 모호해서 무시하도록 바꿨다. 기존 동작과 달라지는 부분이다.
